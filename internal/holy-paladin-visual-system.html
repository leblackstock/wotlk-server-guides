Holy Paladin Visual System

The production specimen for Paladin-first identity, Holy-specific state, healing mechanics, fixed status meanings, and accessible dark-mode components.

RulesPaletteComponentsAccessibility

◆ Hierarchy rules

1. Paladin frames the page

Pink owns the class title, class notes, broad Paladin identity, and general links. It should remain visible without becoming the active-control color.

2. Holy signals state

Gold owns the active chapter, selected filters, Holy-specific controls, summary labels, focus, and technical emphasis.

3. Mechanics keep names

Beacon, direct healing, maintenance, and mana each use a named mechanic token instead of borrowing warning or information colors.

4. Status never changes

Success, warning, danger, and information retain the same meaning on every class and section.

5. Game data stays canonical

Item quality and socket colors remain separate from class, specialization, mechanic, and status roles.

6. Text carries meaning

Every color-coded item includes a label, icon, border, position, or wording. Color alone never carries an assignment.

◆ Accessibility and regression gate

  • All interactive controls receive visible keyboard focus and a non-color pressed state.
  • Selected filters use aria-pressed; status counts use live regions.
  • Every mechanic lane carries text labels and structural borders.
  • Mobile grids collapse without horizontal page overflow; wide tables scroll inside their containers.
  • Print removes ambient gradients and shadows while preserving labels and hierarchy.
  • Holy pages load the shared Paladin layer directly. Existing Tankadin CSS remains untouched in this release so the new guide cannot regress the live Protection pages.
Approval target: this page is the Holy visual contract. New Holy components must map to one of these roles or introduce a documented token before use.
